# 核心信念

这些是 Routa「以仓库为系统记录源（repository-as-system-of-record）」方向背后的运作信念。

## 1. 仓库承载工作知识

如果一个 Agent 在运行时无法从仓库中发现某项决策，那么这项知识在运作层面就等于不存在。

实践推论：
- 持久的产品、架构和质量知识应当存放在 `docs/` 中
- 聊天记录、口口相传的经验和私人笔记不被视为权威来源

## 2. `AGENTS.md` 是一个路由层

`AGENTS.md` 应当保持精简。它应当告诉 Agent 去哪里查找、必须遵循哪些规则，以及适用哪条验证回路。

实践推论：
- 把详细说明排除在 `AGENTS.md` 之外
- 添加指向正确 `docs/` 位置的指针，而不是无限制地扩充本地说明

## 3. 每一类知识只有一个权威归处

每一项长期存在的事实都应当有一个明确的归处。

实践推论：
- 产品表面（product surface）存放在 `docs/product-specs/`
- 架构存放在 `docs/ARCHITECTURE.md`
- 设计意图存放在 `docs/design-docs/`
- 进行中的计划存放在 `docs/exec-plans/`
- 故障与回归存放在 `docs/issues/`

## 4. 优先优化 Agent 可读性

文档应当便于 Agent 扫读、引用并据以行动。

实践推论：
- 优先使用明确的标题、简短的章节和稳定的文件名
- 避免把关键规则埋藏在冗长的叙述性文档中
- 引用源材料时使用直接的文件名和路径

## 5. 偏好持久规则，而非提示词口耳相传

如果某种行为反复出现且很重要，就把它编码进仓库结构、检查或有文档记录的不变量中。

实践推论：
- 在可能的情况下，把反复出现的预期迁移到 linter、测试、适应度函数或黄金规则（golden rules）中
- 不要仅依赖 Agent 记忆或 issue 评论来承载关键约束

## 6. 通过规范化迁移，而非通过复制迁移

历史设计文档是有用的输入，但不会自动成为权威输出。

实践推论：
- `.kiro/specs/` 可以作为出处保留，同时对其内容进行审阅
- 优先迁移摘要、不变量和决策
- 避免创建会彼此漂移的重复文档

## 7. 反馈必须进入记录

Bug、回归和质量缺陷应当产生供后续 Agent 使用的仓库工件。

实践推论：
- 在 `docs/issues/` 中记录事件
- 把 issue 记录、计划、测试和实现工作彼此关联起来
- 把事后复盘证据视为交付的一等组成部分
