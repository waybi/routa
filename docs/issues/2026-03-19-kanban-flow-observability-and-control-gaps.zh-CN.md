# 看板缺乏流动可观测性、可控性与优化原语

## 发生了什么

Routa 的看板在 Agent 原生的工作流执行方面已经很强：

- 列（column）的流转由系统解释，而不仅仅是在 UI 中渲染
- 卡片可以触发专家（specialist）自动化
- 任务保留泳道会话历史与交接历史
- 卡片可以绑定到代码库、会话和 git worktree

然而，与成熟的看板实践在 SDLC 流动管理上的做法相比，该看板仍然缺少理解和改进交付流动所需的运营原语。

当前实现的行为更像是一个 Agent 执行控制平面，而不是一个流动管理系统。

## 为什么这很重要

如果没有显式的流动指标和控制机制，系统可以执行工作，但无法可靠地回答：

- 工作在哪里堆积
- 哪些列过载
- 哪些任务的滞留时间超出预期
- 有多少时间花在阻塞状态
- 交付是否变得更可预测还是更不可预测

这就在「工作流可计算」和「工作流可治理、可优化」之间留下了一道鸿沟。

## 观察到的差距

### 1. 缺少一等公民级的流动指标

任务模型和看板模型没有暴露一等公民级的看板流动原语，例如：

- 按列 / 泳道 / 看板划分的 WIP
- 按时间窗口划分的吞吐量
- 周期时间（cycle time）
- 前置时间（lead time）
- 工作项滞留时长（work item age）
- 阻塞时长（blocked time）
- SLE 达成率

### 2. 缺少显式的控制面

看板支持自动化和产物要求，但缺少显式的运营约束，例如：

- 每列的 WIP 限制
- 泳道级别的容量策略
- 服务类别（service classes）
- 基于滞留时长的升级规则
- 按工作类型或泳道划分的 SLE 目标

### 3. 阻塞状态的结构化程度不足

阻塞流转已经存在，但被阻塞的工作并没有用支持分析和治理的结构化字段建模，例如：

- 阻塞原因
- 阻塞类别
- 阻塞负责人
- 阻塞起始时间 / 解除阻塞时间
- 解决摘要

### 4. 门禁大多只是存在性检查

当前的门禁（gate）行为主要验证产物是否存在。它并没有一致地强制执行策略层面的判断，例如验证是否真正通过。

### 5. UI 缺少流动仪表盘

工作区的看板 UI 在执行上下文以及 worktree/会话操作方面很强，但它没有提供专门的流动视图来呈现：

- WIP 与限制对比
- 滞留项
- 阻塞分布
- 吞吐量趋势
- 周期/前置时间分布
- 累积流图（cumulative flow）
- SLE 合规情况

## 产品影响

这限制了 Routa 的定位。

如今该产品可以可信地宣称：

- 「看板是可执行的」
- 「工作流是 Agent 感知的」

但它还不能完整地宣称：

- 「流动是可度量的」
- 「系统可以强制执行拉动（pull）纪律」
- 「看板能够展示瓶颈与可预测性」

## 建议方向

下一个看板里程碑应聚焦于增加：

1. 面向看板流转和阻塞/解除阻塞时段的持久化流动事件模型
2. 显式的看板/列控制原语，例如 WIP 限制和 SLE 策略
3. 结构化的阻塞状态数据
4. 基于策略的门禁，而不仅仅是产物存在性检查
5. 工作区 UI 中的流动可观测性仪表盘
