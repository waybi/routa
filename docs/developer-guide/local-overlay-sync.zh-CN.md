# 本地叠加层与上游同步

本指南面向那些在本地运行 Routa、需要少量仅本地的修复或运维调整，同时又希望上游更新能够保持轻松同步的团队或 Agent。

目标很简单：

- 让 `upstream/main` 保持为干净的唯一可信来源
- 把仅本地的行为集中在一个轻量的叠加层分支里
- 保留一份干净的工作副本，用于日常拉取、检查和比对

这样可以避免一种常见的失败模式：长期存在的功能分支、若干临时 worktree，以及未提交的本地改动，全部混进同一个「真实」环境里。

## 何时使用此模式

当以下条件全部成立时，使用此模式：

- 你在自己的环境中运行 Routa
- 你需要尚未进入上游的本地行为
- 你仍打算持续拉取上游更新
- Agent 或运维人员可能在同一台机器上发起本地修复和上游 PR

**不要**把此模式用于一次性的临时实验。它适用于需要保持可升级性的本地部署。

## 推荐的分支模型

使用职责清晰的三条通道：

1. `upstream/main`
   - 仅用于 fetch
   - 绝不携带仅本地的修改
2. `local/routa-overlay-*`
   - 唯一长期存在、承载仅本地行为的分支
   - 当上游变更时，将其 rebase 到 `upstream/main` 上
3. 临时的 issue 或 PR 分支
   - 用于隔离的缺陷修复、实验或上游贡献
   - 合并或被拒绝后即删除

重要规则是：仅本地的行为不应存在于你的默认日常分支中，也不应以未提交的形式留在主 worktree 里。

## 推荐的工作副本布局

保留两份持久的工作副本：

- 一份**干净的 main worktree**，固定指向最新的 `upstream/main`
- 一份**叠加层 worktree**，用于 `local/routa-overlay-*`

干净的 worktree 用于：

- 拉取上游
- 检查上游是否已经修复了某个 bug
- 在不带本地补丁的情况下复现行为
- 准备面向上游的 PR

叠加层 worktree 用于：

- 本地运行时修复
- 本地运维工作流变更
- 你有意保留在上游之外的、特定于环境的行为

临时 PR 分支可以放在短生命周期的 worktree 中，用完后应当移除。

## 如何捕获本地改动

当你发现某些本地改动必须在未来的更新中存活下来时：

1. 停止往默认 worktree 中追加更多未提交的修改
2. 对改动进行分类：
   - 可上游化的修复
   - 仅本地的运行时行为
   - 不应提交的本地机器状态
3. 仅将仅本地的代码或文档迁移到 `local/routa-overlay-*`
4. 以小而可评审的提交将它们提交

不要提交：

- 数据库
- 日志
- 缓存
- 运行时状态
- 密钥
- `.env` 文件
- 机器本地的临时目录

如果某项改动是可上游化的，优先开一个独立的 PR 分支，而不是把它折叠进叠加层。

## 如何与上游同步

每次上游变更时使用此流程：

```bash
git fetch upstream
git switch main
git reset --hard upstream/main
git switch local/routa-overlay-YYYY-MM-DD
git rebase upstream/main
```

rebase 之后：

- 只解决叠加层特有的冲突
- 为 rebase 后的叠加层重新运行所需的检查
- 当上游已经吸收了某些叠加层提交时，缩减或删除它们

如果上游已经包含了相同的修复，不要仅仅因为本地补丁创建得更早就保留一份重复的补丁。

## 如何准备上游 PR

当某项本地修复应当进入上游时：

1. 从干净的 `upstream/main` worktree 开始
2. 为该修复创建一个临时分支
3. 保持 PR 范围最小化
4. 仅验证该范围所需的检查
5. 推送到你的 fork
6. 开启 PR

在开启 PR 之前，检查上游是否已经解决了相同的问题：

```bash
git fetch upstream
git log --oneline upstream/main..HEAD
gh api repos/<upstream-owner>/<repo>/compare/main...<your-fork-owner>:<branch>
```

如果 compare 显示没有有意义的提交可供贡献，就不要开启重复的 PR。

## Agent 运维检查清单

如果你使用 Agent 来管理本地的 Routa 检出，请明确遵守这些规则：

- 必须始终存在一份干净的上游 worktree
- 必须只有一个叠加层分支作为唯一长期存在的本地补丁层
- PR 工作必须在临时分支上进行，而不是在叠加层分支上
- 机器本地状态绝不能包含进 PR
- 在开启 PR 之前，Agent 必须检查上游是否已经修复了该问题
- 在上游接受某项修复之后，Agent 应当移除或缩减对应的叠加层补丁

这样可以让本地自托管使用与上游协作彼此兼容，而不是相互冲突。
