# 代码风格

## 核心理念
- 优先以领域对象来思考，而不是优先以辅助函数来思考。
- 倾向于「薄外壳 + 厚内核」的结构：CLI/API/UI 应主要负责分发，而真正的逻辑应位于 core/usecases 中。
- 以显式性、可读性以及交付价值为优化目标，而非追求巧妙的抽象。
- 即使需要手写序列化或显式的转换代码，也要保持稳定的数据/文件/输出契约。

## 项目组织
- 按领域职责组织模块，例如 `entry`、`usecases`、`parser`、`transflow`、`server`、`cli`、`helper`。
- 模块和数据结构用名词命名；函数用动词命名。
- 保持入口点轻薄，将可复用的逻辑下沉。

## Rust 风格
- 倾向于使用字段清晰、领域命名强的简单 struct/enum。
- 在有帮助时，可以自由地为领域模型派生 `Serialize/Deserialize/Debug/Clone/Default`。
- 当文件系统结构或字段顺序重要时，倾向于使用 `PathBuf`、有序 map 以及显式的辅助类型。
- 当巧妙的迭代器链会损害可读性时，优先使用直白的 `for`、`if` 和 `match`。
- 在公共边界返回 `Result`，并为领域失败使用自定义的业务错误。
- 当文本格式本身就是产品契约的一部分时，手写格式化/解析是可以接受的。
- 优先使用中小型函数，但当较大的编排/代码生成函数能让工作流在一处保持可读时，它们也是可以接受的。

## 错误处理
- 务实为先：在边界处保留错误，但不要对每个内部分支都过度设计。
- 仅在不变量确实足够强时，才在内部使用快速失败（fail-fast）的假设。
- 避免那些会掩盖业务流程的装饰性错误传递管道。

## 测试
- 倾向于围绕真实工作流、fixture、文件 IO、解析以及生成输出的行为驱动测试。
- 测试端到端的功能切片，而不仅仅是孤立的纯函数。
- 测试名称应清晰描述行为，例如 `should_create_*`、`parse_*`、`update_*`、`crud_*`。

## TypeScript / 前端风格
- 倾向于编写能与浏览器和各类库良好集成的务实组件代码。
- 直接使用 hooks 或组件状态；除非确有复用需求，否则让逻辑贴近组件。
- 在框架边界处容忍命令式的 DOM/事件集成。
- 优先使用可读的本地辅助函数，而非过早抽象。
- 当能让组件保持自包含时，使用 styled-components 或类似的局部样式方案。

## 命名
- 使用领域感强的名称，如 `create_entry`、`update_entry_properties`、`feed_entry`、`parse_action`、`gen_transform`。
- 按事物在业务/工作流中的含义来命名，而不是用通用的技术标签。

## 应避免
- 除非抽象层能明显降低领域复杂度，否则不要引入它们。
- 不要以牺牲清晰控制流为代价去追求语言上的炫技。
- 不要把重要的数据转换隐藏在魔法般的辅助函数背后。
- 不要过度迁就遗留产物，例如滥用 `any`、`@ts-ignore` 或嘈杂的 `unwrap/expect`。
