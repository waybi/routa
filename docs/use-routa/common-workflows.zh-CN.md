# 常见工作流

这些是在完成安装并且有一个 Provider 正常工作之后，使用 Routa 的最常见方式。

## 理解一个新代码库

当你进入一个不熟悉的仓库，并希望以最快的路径建立起有用的心智模型时，使用这条路径。

1. 打开一个工作区并挂载仓库。
2. 从 [Sessions](/use-routa/sessions) 开始。
3. 在请求具体实现之前，先请求一个高层次的总览。
4. 如果你需要的是产品模型，而不仅仅是仓库结构，则转到 [Core Concepts](/core-concepts/how-routa-works)。

在以下情况使用此工作流：

- 你需要在修改代码之前先建立方向感
- 你希望有一条可恢复的线程
- 工作仍处于探索阶段

## 实现一个具体任务

当任务明确，且暂时不需要工作流阶段时，使用这条路径。

1. 打开一个工作区。
2. 让一个 Provider 可用。
3. 启动一个[会话](/use-routa/sessions)。
4. 给 Routa 一个具体的实现请求。
5. 审查结果，然后要么在同一会话中继续迭代，要么开启一个新会话。

这是以下场景的默认路径：

- 功能实现
- 缺陷修复
- 文档更新
- 短小的代码库重构

## 推动工作流经交付阶段

当工作受益于明确的待办、开发、评审和完成边界时，使用这条路径。

1. 打开工作区看板。
2. 创建或细化任务。
3. 在[看板](/use-routa/kanban)泳道之间移动卡片。
4. 让阶段流转和泳道策略驱动下一步执行。

在以下情况，这是合适的工作流：

- 多个任务共享同一套交付模型
- 你希望评审和完成的行为像真正的关卡一样
- 交接的可见性比单线程的便利更重要

## 协调多专家工作

当协调问题本身就是头等大事时，使用这条路径。

1. 启动 [Team](/use-routa/team)。
2. 谨慎地选择仓库或工作区上下文。
3. 让 Lead 将工作委派给各个专家。
4. 将进展作为受协调的子工作来审查，而不是作为单一线程。

在以下情况，这是最合适的：

- 前端、后端、QA 或运维等关注点需要分离
- 多个代码区域需要并行推进
- 单一主会话会变得过于臃肿

## 在不丧失势头的情况下调整设置

当 Routa 已安装，但执行因配置而被阻塞时，使用这条路径。

1. 打开 [Configuration](/configuration)。
2. 让一个 Provider 可用。
3. 仅当你的 Provider 需要时，才添加一条模型路径。
4. 返回你的工作区，继续使用 `Session`、`Kanban` 或 `Team`。

不要把设置当成每个 Provider 都要走一遍的前置检查清单。有一条能用的路径就足够了。
