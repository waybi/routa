## 第一章 定位与差异化

**一句话**：你的本地 AI 开发团队——把需求扔进看板，验收就行。

Koda 是一个 local-first 桌面应用。用户的角色从"结对程序员"升级为"技术负责人"：定需求、看验收；中间的开发、测试、审查由 AI 团队在隔离工作区里并行完成。

**三个差异化立足点：**

| 对比对象 | Koda 的不同 |
|---|---|
| Claude Code / 对话式 agent | 它们是"一次一个对话"的结对，人必须守着屏幕；Koda 是"多卡并行"的工厂，人脱离环，只在验收点回来 |
| Devin / 云端 agent 平台 | Koda 全本地：代码不出机器、模型可换（Anthropic 兼容 API + 第三方）、执行过程透明、随时可接管 |
| Jira / Linear 等看板工具 | 卡片不是记录，是活的执行单元——列流转由状态机自动驱动，人的动作只有三种：进料、验收、裁决异常 |

**产品哲学（三条，来自两个上游项目的核心洞察）：**

1. **工作项是一等公民，会话是附属**（Routa）：系统的真相住在卡片和任务图里，不住在聊天记录里。
2. **人的注意力是最稀缺资源**（本产品新增）：一切设计以"减少人的介入次数和时长"为最高优先级；打断必须有充分理由。
3. **过程透明、随时可接管**（cc-haha）：自动化不是黑盒，每张卡的每一步可观察、可回放、可插手。

## 第二章 目标用户与使用场景

**目标用户（v1 就一个人）**：拥有多个个人/工作项目的开发者，日常有一批"想做但排不上"的需求积压，愿意把机械性开发工作委托给 AI，但要求最终质量由自己把关。

### 场景故事 A：早晨进料（每天的开始）

老魏早上打开 Koda，选中 `koda` 项目。他在看板顶部的进料口敲了一段话："给验收台加键盘快捷键支持，j/k 切换卡片，a 通过，r 打回；另外状态栏的成本统计改成本周累计。" 按下回车。

20 秒后，Planner 给出拆卡预览：3 张卡——`快捷键基础设施`、`验收台快捷键接入`（依赖前者）、`状态栏成本改造`（独立）。每张卡带目标、验收标准、预估涉及文件。老魏扫了一眼，把第二张卡的验收标准改了一句，点"全部入场"。三张卡落进 Backlog，其中两张（无依赖的）立即自动进入 Dev 列开工。全程 3 分钟。

### 场景故事 B：白天脱离（产品的核心承诺）

老魏去干自己的正事了。期间：`快捷键基础设施` 卡完成开发 → 自动进 Review 列 → AI 审查员对照验收标准查 diff、跑测试 → 发现一个边界 bug → **自动打回 Dev 带审查意见 → agent 修复 → 再次审查通过** → 进"待验收"列。这个打回循环发生了两次，老魏毫不知情，也不需要知情。

下午三点，系统桌面通知："2 张卡待验收"。这是老魏今天第一次被打断。

### 场景故事 C：五分钟验收

老魏点开通知进入验收台。左侧队列 2 张卡，中间全宽 diff，右侧验收标准 checklist（AI 审查已逐项打勾并附证据）。第一张卡他扫了 diff，按 `a` 通过——卡片按项目配置自动 squash 合并回 main，worktree 清理，进 Done。第二张他觉得快捷键提示的 UI 位置不对，按 `r` 打回，输入一句评语。卡片带着评语回到 Dev 列，agent 在原 worktree 上继续修。老魏关掉窗口继续干活。全程 5 分钟。

### 场景故事 D：求助与接管（异常路径）

某张卡的 agent 在实现时发现两种互斥方案（迁移数据表 vs 兼容旧格式），拿不准。它不瞎猜，而是**升级求助**：卡片打上"求助"标记（留在原列），出现在收件箱。老魏收到通知，点开卡片看到 agent 的提问和两个方案的利弊。他直接在卡片详情的活动流里回了一句"走迁移，旧数据不多"。agent 收到后继续。如果问题更复杂，老魏可以点"接管"——在新标签页打开完整会话，像用 Claude Code 一样直接指挥；接管期间卡片标记"人在环"、暂停自动调度，聊完点"交还"，卡片回到自动流。

## 第三章 核心对象模型

### 3.1 对象与关系

```text
Workspace（项目）
 ├─ 1:1  Repo（git 仓库；v1 一项目一仓库，模型预留 repoIds[] 多仓库字段）
 ├─ 1:1  Board（看板；5 固定列）
 ├─ 1:N  Card（工作项 = 系统的一等公民）
 └─ 1:N  Specialist（agent 角色定义：planner / developer / reviewer，可加自定义）

Card（卡片）
 ├─ 属性：title / objective / acceptanceCriteria[] / columnId / state /
 │        overlayFlags[]（FAILED/HELP/PAUSED/TAKEN_OVER 叠加标记）/
 │        dependsOn[]（卡片依赖 DAG）/ priority（high/normal/low）/
 │        manualOrder（Backlog 内手动排序）/ costBudget / createdFrom
 ├─ 1:1  Worktree（隔离工作区；per-card 而非 per-run——打回重修在同一
 │        worktree 继续，保留已有改动；验收合并后清理）
 ├─ 1:N  Run（一次执行 = 一个 agent 会话；打回/重试产生新 Run，历史全保留）
 └─ 1:N  InboxItem（该卡产生的通知/求助/告警）

Run（一次执行）
 ├─ 属性：kind（plan / develop / review / fix）/ state / specialistId /
 │        model / tokenUsage / startedAt / endedAt
 └─ 1:1  Session（会话 = 消息流 + 工具调用流水；可回放、可接管续聊）

InboxItem（收件箱条目）
 └─ 类型：AWAITING_ACCEPTANCE（待验收）/ HELP（求助）/ FAILED（失败告警）
          / BUDGET（成本超限）——只有这四类会打扰人
```

**关键建模决策：**

- **Card 与 Run 分离**（继承 Routa 的 Task/BackgroundTask 双生命周期）：卡片表达"业务做到哪"，Run 表达"这一轮执行跑到哪"。一张卡被打回 3 次 = 1 张卡 + 4 个 Run，历史完整。
- **Worktree 挂在 Card 上**：打回重修必须看得见上一轮的改动，所以工作区跟卡走，不跟 Run 走。
- **收件箱条目是显式对象**：不是"通知过就没了"的 toast，而是有生命周期（未读/已处理）的待办，跨项目聚合。
- **状态与叠加标记分离**：`state` 表达主流转进度（决定卡片在哪一列）；`overlayFlags` 表达异常/介入（FAILED/HELP/PAUSED/TAKEN_OVER），不改变所在列，消除后回到标记前状态继续。

### 3.2 卡片状态机（产品的骨头）

```text
                    ┌────────────────────────────────────────────────┐
                    │        列 ↔ 状态映射（固定 5 列）                 │
                    │  Backlog: QUEUED / BLOCKED                      │
                    │  Dev:     READY / RUNNING / FIXING              │
                    │  Review:  REVIEWING                             │
                    │  待验收:   AWAITING_ACCEPTANCE / MERGING         │
                    │  Done:    DONE / CANCELLED                      │
                    │  （DRAFT 不上看板，只存在于拆卡确认面板；           │
                    │    FAILED/HELP/PAUSED/TAKEN_OVER 是叠加标记，    │
                    │    卡留在原列）                                  │
                    └────────────────────────────────────────────────┘

DRAFT（拆卡预览，未入场，不上看板）
  │ 用户确认入场
  ▼
QUEUED（依赖未齐或等槽位）──依赖卡失败/取消──▶ BLOCKED（显式阻塞，收件箱可见）
  │ 依赖全部 DONE 且抢到并发槽位                  │ 用户解除依赖/重开上游
  ▼                                            ▼（回 QUEUED）
READY（已占槽，待派发）
  │ 派发 developer agent
  ▼
RUNNING（developer 在 worktree 干活）
  │ agent 宣告完成            │ 超时/崩溃 ▶ FAILED*
  ▼                          │ agent 求助 ▶ HELP*
REVIEWING（reviewer 对照验收标准查 diff + 跑测试）
  │ 通过                      │ 不通过（自动，不惊动人）
  ▼                          ▼
AWAITING_ACCEPTANCE ◀──再次通过── FIXING（原 worktree 修复，新 Run）
  │                                  │ 累计打回 ≥3
  │ 人验收                            ▶ HELP*（升级人裁决）
  ├─────────┴─────────┐
  ▼ 通过(a)            ▼ 打回(r, 附评语)
MERGING ──成功──▶ DONE   └──▶ FIXING（带人的评语，新 Run）
  │ 冲突
  ▼
系统 rebase 任务尝试一次 ──失败──▶ HELP*（人裁决冲突）

* FAILED / HELP / PAUSED(成本超限) / TAKEN_OVER(人接管中) 均产生 InboxItem，
  等待人处理；处理后回到标记前状态继续。任何非终态可被人取消 → CANCELLED。
```

**状态 × 列 × 触发者 × 副作用总表**（闭环定义，状态机实现以此为准）：

| 状态 | 所在列 | 进入触发（触发者） | 副作用 |
|---|---|---|---|
| DRAFT | 不上看板（拆卡确认面板） | planner 产出（系统） | 无 worktree、无 Run；"全部入场"后此态销毁 |
| QUEUED | Backlog | 用户入场（人）/ 依赖未齐或等槽位（系统） | 无 |
| BLOCKED | Backlog | 依赖卡 FAILED/CANCELLED（系统） | 产生 InboxItem；解除依赖/重开上游后回 QUEUED |
| READY | Dev | 依赖全 DONE 且抢到全局槽位（调度器） | 占用槽位；首次进入时创建 worktree |
| RUNNING | Dev | 派发 developer（系统） | 新 Run(kind=develop)；卡片显示 liveMessageTail |
| FIXING | Dev | review 不通过（系统）/ 人验收打回（人） | 新 Run(kind=fix)，同一 worktree；审查意见/人评语注入会话 |
| REVIEWING | Review | developer 宣告完成（agent） | 新 Run(kind=review，只读+跑测试)；产出结构化审查报告；不占开发槽位 |
| AWAITING_ACCEPTANCE | 待验收 | review 通过（系统） | 释放开发槽位；InboxItem(AWAITING_ACCEPTANCE) + 桌面通知 |
| MERGING | 待验收（"合并中"标记） | 人验收通过（人） | 系统 merge 任务按 deliveryMode 执行；冲突 → 系统 rebase 尝试一次 → 失败则 HELP |
| DONE | Done | merge/PR/推分支成功（系统） | worktree 清理；成本归档 |
| CANCELLED | Done（灰显） | 人取消，任意非终态可达（人） | 终止进行中的 Run、释放槽位、清理 worktree（可选保留分支） |

**叠加标记**（不产生列移动，均产生 InboxItem，消除后回标记前状态）：

| 标记 | 触发 | 消除方式 |
|---|---|---|
| FAILED | watchdog 超时 / agent 崩溃 / 重启 reconcile 发现孤儿 Run | 人：重试（新 Run 原 worktree）/ 改卡后重试 / 取消 |
| HELP | agent 主动求助 / 累计打回 ≥3 / rebase 失败 | 人：轻回复（原 Run 继续）/ 接管 / 裁决后取消 |
| PAUSED | 单卡 token 成本超预算 | 人：加预算（回标记前状态）/ 取消 |
| TAKEN_OVER | 人点"接管" | 人点"交还"：回自动流，必要时开新 Run |

**防死循环规则**：AI 审查打回同一张卡累计 ≥3 次 → 强制升级 HELP，人裁决。防止 developer 和 reviewer 无限拉锯烧钱。

### 3.3 人的动作全集（人可执行动作矩阵）

人在系统里只有这些动作，除此之外一切自动：

| 动作 | 可用状态 | 结果 |
|---|---|---|
| 进料 / 确认拆卡入场 | —（产生 DRAFT → QUEUED） | 新卡落 Backlog |
| 编辑卡片字段 | DRAFT / QUEUED / BLOCKED | 直接生效；RUNNING 之后改验收标准 → 下次 review 生效并提示"标准已变更" |
| Backlog 内拖拽排序 | 仅 Backlog 列内 | 写 `manualOrder`，影响调度出队顺序（见 §3.4） |
| 验收通过（a） | AWAITING_ACCEPTANCE | → MERGING |
| 验收打回（r，附评语） | AWAITING_ACCEPTANCE | → FIXING，评语注入新 Run |
| 回复求助（轻回复） | HELP | 回答注入原 Run，agent 继续 |
| 接管（t）/ 交还 | 任意非终态 | TAKEN_OVER 标记 +/-；接管期间该卡暂停自动调度、释放槽位，交还后重新入队 |
| 重试 | FAILED | 新 Run，原 worktree |
| 加预算 | PAUSED | 回标记前状态 |
| 解除依赖 / 重开上游 / 连锁取消 | BLOCKED | 回 QUEUED / 上游重入队 / 下游连锁 CANCELLED |
| 取消 | 任意非终态 | → CANCELLED |

**手动拖卡规则（v0.3 裁定）**：拖拽仅限 **Backlog 列内排序**（调整 `manualOrder`）。**禁止跨列拖动**——列流转只由状态机和上表中人动作驱动，杜绝"拖动即指令"与列级门禁的语义冲突。

### 3.4 调度语义（v0.3 裁定）

- **并发槽位**：全局唯一槽位池，默认 2，可配。只有 develop/fix 类 Run（READY/RUNNING/FIXING）占槽；review Run 与 plan Run 轻量、不占槽，但同一卡同一时刻最多一个 Run。
- **出队顺序**：`priority` 降序（high > normal > low）→ `manualOrder` 升序（Backlog 拖拽结果）→ `createdAt` 升序。
- **依赖门**：`dependsOn` 全部 DONE 才参与出队；任一依赖 FAILED/CANCELLED → 本卡 BLOCKED。
- **priority 不进 SLA、不做抢占**：只影响排队顺序，不打断已在跑的卡。

### 3.5 交付策略（v0.3 裁定）

- 项目级设置 `deliveryMode`，三档：**`auto-merge`（默认）** = 验收通过即 squash 合并回 main；**`pr`** = 系统任务建 PR，卡片标 PR 链接后 DONE（人等 CI/手动合）；**`branch`** = 仅推分支，DONE 后留人处理。
- 合并冲突处理：**系统内置 rebase 任务**（确定性 git 操作，非 specialist，不占槽、不产生 Run 会话页），自动尝试一次；失败 → HELP 升级人裁决。

## 第五章 核心交互流

### 流 1：进料（planner 拆卡）

1. 进料口输入需求（支持粘贴 issue 链接/长文）→ 回车。
2. Planner Run 启动（只读权限扫代码库），进料口下方展开"拆卡中…"面板，流式显示思考摘要。
3. 产出卡片组预览：每卡 = 标题 + 目标 + 验收标准 + 预估涉及文件 + 依赖连线。
4. 人可以：编辑任意字段 / 删卡 / 合并卡 / 补卡 / 调整依赖。
5. "全部入场" → 卡落 Backlog，依赖就绪的立即流转。**快捷通道**：进料口输入时按 `⌘↵` = 跳过 planner 直接手写单卡（小事不值得跑 planner）。

**验收标准质量门槛（v0.3 新增）**：planner 被要求为每张卡产出至少 1 条**可机器验证**的验收标准（形如"运行 X 测试通过""文件 Y 导出 Z"）。拆卡确认面板对空标准或纯主观描述的卡标黄警告；reviewer 对无法机器核验的标准标记"需人工判断"，验收台对应条目高亮提示人重点看。

### 流 2：自动执行（人不在场）

QUEUED → READY 由调度器驱动（依赖门 + 全局槽位，默认 2，出队序见 §3.4）；READY → RUNNING 派发 developer agent 到卡的 worktree；卡片上实时显示"⚡ 最新动作摘要"（liveMessageTail）。完成 → REVIEWING：reviewer agent 对照验收标准逐条核查 + 跑测试，产出结构化审查报告（每条标准：通过/不通过/需人工判断 + 证据）。不通过 → 自动打回 FIXING（附审查意见），同 worktree 新 Run 修复。通过 → 待验收 + 桌面通知。

### 流 3：验收（人回来 5 分钟）

验收台 = 左队列 / 中全宽 diff / 右验收 checklist（AI 审查结果预填 + 证据链接）。快捷键：`j/k` 切卡、`a` 通过、`r` 打回（弹评语框）、`t` 接管、`d` 查看完整 diff。通过 → MERGING（按项目 `deliveryMode`：默认 squash 合并回 main）→ worktree 清理 → DONE。打回 → 评语进入卡片，FIXING 新 Run。

### 流 4：求助与接管

agent 遇到不确定决策 → 调用"升级求助"（这是给 agent 的显式工具，不是异常）→ 卡片加 HELP 标记（留原列）+ 收件箱条目 + 桌面通知。人两种响应：**轻回复**（卡片详情活动流里直接回一句，注入原 Run，agent 继续）/ **重接管**（开会话标签页完整对话，卡片加 TAKEN_OVER 标记、暂停自动调度并释放槽位，聊完点"交还"回自动流）。

### 流 5：失败恢复

- **超时/无进展**（watchdog：可配阈值，默认 30 分钟无工具调用）→ FAILED + 收件箱。人可：重试（新 Run 原 worktree）/ 改卡后重试 / 取消。
- **应用重启恢复**：全部状态在 SQLite。启动时 reconcile：RUNNING 但 agent 进程不在 → 检查 worktree 状态 → 标记 FAILED 待人决定（不自动重跑，防止重复副作用）。
- **成本护栏**：每卡 token 预算（默认继承全局），超限 → PAUSED + 收件箱，人决定加预算或取消。

## 第七章 边界与异常总表

| 异常 | 系统行为 | 人的介入 |
|---|---|---|
| AI 审查打回 ≥3 次 | 强制 HELP，停止自动循环 | 裁决：改验收标准 / 接管 / 取消 |
| 合并冲突（main 已前进） | 系统 rebase 任务自动尝试一次（非 specialist，不占槽） | 失败才升级 HELP 人裁决 |
| agent 超时无进展 | watchdog 标 FAILED | 重试 / 改卡 / 取消 |
| agent 进程崩溃 / 应用重启 | SQLite 恢复 + reconcile，孤儿 Run 标 FAILED | 决定是否重跑（不自动，防重复副作用） |
| 依赖卡失败/取消 | 下游卡显式 BLOCKED（不是永久 PENDING——修 Routa fan-in 债） | 解除依赖 / 重开上游 / 连锁取消 |
| 单卡成本超预算 | PAUSED + 收件箱 | 加预算 / 取消 |
| 不可逆操作（push / rm -rf / 装包外联） | 默认拦截弹审批（唯一的工具级审批） | 批准 / 拒绝 |
| provider 挂了 / 限流 | 卡片停在当前状态 + 状态栏红点，队列不丢 | 等恢复或换模型 |
| 同文件并发冲突 | worktree 天然隔离，冲突只发生在合并时 | 见"合并冲突" |
| 人接管期间调度 | 该卡 TAKEN_OVER：暂停自动调度、释放槽位、不产生新 Run | 交还后重新入队 |
| 验收标准被中途修改 | 下次 review 起生效，卡片详情提示"标准已变更" | 无需介入 |

## 第九章 北极星指标

| 指标 | 目标 | 度量方式 |
|---|---|---|
| **人均介入时间/卡**（北极星） | < 5 分钟 | 拆卡确认时长 + 验收时长 + 求助处理时长 |
| 首次验收通过率 | ≥ 70% | AWAITING → DONE 未经人打回的比例 |
| 无人值守跨度 | ≥ 2 小时 | 相邻两次人操作的最大间隔（工作时段） |

| 卡片端到端成本 | 可见可控 | 每卡 tokenUsage 汇总，预算护栏触发率 < 10% |

**指标产品内可见（v0.3 裁定）**：v1 在设置 → 统计分区展示上述五项，数据全量采集；不做独立报表页。
